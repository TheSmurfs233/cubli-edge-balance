## 2026-11-03 #001 工具链摸底：WSL 不可用于 L1 仿真，改用 Windows uv 环境

### 背景
`workflow/04_仿真先行.md` 要求 L1 离线算法仿真跑在 WSL（Python/Octave）。开工前先验证 WSL 是否具备 numpy/scipy。

### 现象
1. `python3 -c "import numpy"` → `ModuleNotFoundError`。
2. `pip install numpy` 与清华/阿里/中科大镜像全部超时；`getent hosts pypi.org` 返回 `198.18.0.47`（fake-ip 段，说明 DNS 被宿主代理劫持）。

4. `sudo -n apt install` 需要密码，无法自动安装。
5. 同一时刻在 Windows 上 `Invoke-WebRequest https://pypi.org` 返回 **200**。

### 数据
| 项 | WSL Ubuntu-24.04 | Windows |
|---|---|---|
| Python | 3.12.3 | 3.12.14 / 3.11.15 |
| numpy | ❌ | ✅ 2.5.4（uv 环境） |

|---|---|
| K | `[[20.117, 6.421]]` |
| eig(A−BK) | `[-3.17, -3.25]` |
| 结论 | 与手算一致，环境可用 |

WSL 的 Python 是系统自带、无科学计算包，且**无法联网补装**（代理是宿主 Clash 的 TUN/fake-ip 模式，WSL 侧根本出不去）。
继续在 WSL 里挣扎的代价远高于换到 Windows 侧的独立虚拟环境。

### 结论与动作
1. **L1 仿真改在 `D:\Embedded\STM32\cubli\.tmp_env\venv`（uv 创建）里跑**，numpy/scipy/control/matplotlib 齐全。
2. 仿真脚本仍按 POSIX 路径与 `#!/usr/bin/env python3` 写，将来 WSL 若通网可原样搬回，不重写。
3. 硬件在环（L3）本来就在 Windows 侧（串口），不受影响。
4. `.tmp_env/` 加入 `.gitignore`，不提交。

## 2026-11-03 #004 S1 步骤1：CubeMX 工程生成与 4 项配置纠偏

### 背景
S1 第 1 步（执行方=用户）：按 `41_CubeMX配置规格.md` 用 CubeMX 6.18.1 生成 `cubli` 工程。

### 现象
首次生成与基线（`dsh_foc` feature `d7e08b5`）逐文件对比：

## 2026-11-03 #005 USART1 的 DMA 流优先级降到 LOW

### 背景
#004 遗留项：`hdma_usart1_rx/tx` 的流优先级是 `VERY_HIGH`，与编码器 `hdma_spi1_rx` 相同，两者会争 DMA 仲裁。

### 现象 / 问题
IMU 只有 2 KB/s（5 ms 一帧），调试口是人机交互；而 MT6701 每 50 µs 就要一次角度给 20 kHz 电流环用。
四方（USART1×2、USART2×2）与编码器在 DMA1 上抢同一条总线时，`VERY_HIGH` 的串口通道会先占用总线。

### 动作
用户在 CubeMX 的 USART1 → DMA Settings 把两个通道的 Priority 改为 `Low` 并重新生成。

### 数据
改动范围（`git diff` 逐行确认，**只有这两处，无其它副作用**）：

| 文件 | 改动 |
|---|---|
| `Core\Src\usart.c:168` | `hdma_usart1_rx.Init.Priority`: `VERY_HIGH` → `LOW` |
| `Core\Src\usart.c:185` | `hdma_usart1_tx.Init.Priority`: `VERY_HIGH` → `LOW` |
| `cubli.ioc` | `Dma.USART1_RX.0.Priority`、`Dma.USART1_TX.1.Priority` 同步为 `DMA_PRIORITY_LOW` |

改后五个通道的流优先级：

| 通道 | 用途 | 优先级 |
|---|---|---|
| DMA1_CH1 / CH2 | USART1 RX/TX（IMU） | LOW |
| DMA1_CH3 / CH4 | USART2 RX/TX（调试） | LOW |
| DMA1_CH5 | SPI1 RX（MT6701 编码器） | **VERY_HIGH** |

### 结论
现在只有编码器拿最高流优先级，与"电流环 20 kHz 等不起"的事实一致。

- [x] `.c` 与 `.ioc` 双向一致（三个文件项全部同步）
- [x] `git diff --stat` 仅 2 文件 4 行，无意外改动
- [x] 增量编译 `-b`：0E / 0W（`build_s1_step1_f.log`，18 s）
- [x] 删输出目录全新编译 `-r`：0E / 0W，`Code=15726 RO=570 RW=20 ZI=2804`（`build_s1_step1_g.log`，20 s，数字可复现）

### 现象 / 问题
不能直接从 `dsh_foc` 工作区复制文件：工作区可能有未提交改动，复制后无法说明"这是哪一版代码"。
也不能让 CubeMX 重新生成工程：`myfoc.uvprojx` 被手工改过 12 次，重生成会丢 `User` 分组与 include 路径。

### 动作
1. **从提交导出而不是从工作区复制**：
   `git -C D:\Embedded\STM32\dsh_foc archive --format=zip -o .tmp_user.zip d7e08b5 User`
   → `Expand-Archive` 到仓库根 → 删 zip。这样进来的文件与 `d7e08b5` 逐字节一致。
2. **工程文件用脚本改，不手改**：`.tmp_env\patch_uvprojx.py` 把 `myfoc.uvprojx` 里 `<Group>User</Group>`
   整块（26 个 `.c`）原样插到 `Drivers/STM32G4xx_HAL_Driver` 分组之前，再把 `IncludePath`
   换成合并后的 10 条。改完打印分组与文件数自证。

### 数据
- 文件数：**54**（`Alg` 16 / `App` 4 / `Bsp` 20 / `Cfg` 2 / `Mid` 12），与 `git ls-tree -r d7e08b5 User` 一致
- 分组（改后）：`Application/MDK-ARM` 1、`Application/User/Core` 9、**`User` 26**、`Drivers/STM32G4xx_HAL_Driver` 22、`Drivers/CMSIS` 1
- `IncludePath`：`../Core/Inc;../User/Cfg;../User/Bsp;../User/Mid;../User/Alg;../User/App;../Drivers/STM32G4xx_HAL_Driver/Inc;../Drivers/STM32G4xx_HAL_Driver/Inc/Legacy;../Drivers/CMSIS/Device/ST/STM32G4xx/Include;../Drivers/CMSIS/Include`
- 编译：26 个 `User` `.c` 全部出现在编译日志
- 构建 `-r`（`build_s1_step2.log`，29.4 s）：**ExitCode=0，0 Error(s)，0 Warning(s)**，
  `Code=17336 RO-data=568 RW-data=72 ZI-data=8320`

### 分析
`Code` 只有 17.3 KB，远低于 `dsh_foc` 基线的 64.6 KB。原因：`main.c` 还没接回 `app_init()`/`app_loop()`，
而工程开了 `OneElfS=1`（每个函数独立段），链接器把不可达函数整段丢掉了。
**所以步骤 2~3 的 0E0W 只证明"能编译"，不证明"能链接、能跑"**——真正的验证要等步骤 4 接回入口，
届时 `Code` 应跳回 60 KB 量级，这一步必须复测。
